# Unity Code MCP Server 0.5.2 Release Changes

## TL;DR

- New **copy-paste agent setup guide** in the README: hand it to Claude Code or Codex and the agent installs the package and registers the MCP server for you.
- The `executing-csharp-scripts-in-unity-editor` skill now teaches the **domain-reload timing discipline** that was the most common cause of spurious agent timeouts.

## 📚 Docs

- Rewrote the README around getting started fast. Removed the inherited upstream fork changelog (that history lives in `Dev/Releases/`) and added an **Agent setup** section — a self-contained prompt that an MCP-capable agent can execute end to end (install `uv`, add the UPM dependencies, register the stdio bridge with correct timeouts).
- Documented that the bridge is a standard **stdio** MCP server. It registers as a local server (via `claude mcp add` or a Codex `[mcp_servers.*]` block), not as a remote "Connector".

## 🧠 Skill

`executing-csharp-scripts-in-unity-editor` gains a **Compilation & Domain Reload Discipline** section:

- A request that arrives mid-reload is deferred, not rejected, so a single tool call can legitimately block for the whole recompile — that is expected, not a hang.
- **One call, then wait** — do not cancel and re-issue; the bridge is single-flight and duplicates only pile up.
- The MCP client's per-tool timeout must be **>= the bridge `--request-timeout`**. In Codex, `tool_timeout_sec` defaults to **60s**, which is shorter than a full recompile, so the client aborts before Unity answers — set it to 240+. (Claude Code has no such low cap, which is why it "just worked" while Codex timed out.)
- On a "compiling / compiler errors" result, read the console and fix the source before retrying instead of spamming the same call.

No Unity runtime behavior changed. Update the package to pick up the new skill text.
